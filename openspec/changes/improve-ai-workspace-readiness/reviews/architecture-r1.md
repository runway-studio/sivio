# 架构质量门：第一轮

- 日期：2026-10-28
- 审查对象：brief/proposal/design/tasks/acceptance 及全部增量 spec；对照现有 session、forwarder、outbound、profile、sync_protocol、restore_journal、database schema。
- 方式：独立静态审查；未运行产品、未调用真实供应商、未修改业务代码。
- 结论：**需修订**。0 个 P0、5 个 P1；修订以下契约后可直接实施，不需要增加平台或通用框架。

## 已确认的合理取舍

- 每客户端当前 Profile 的作用域、请求级出站快照、能力三态、观察费用准入及本机/同步数据隔离均符合现有结构。
- 同供应商多模型已正确要求候选身份贯穿 forwarder，而不只删除表单去重。
- 选择恢复复用暂存合并与现有 journal、放弃跨资源瞬时原子承诺，方向合理。
- 延续四客户端网关范围、已有五策略与按请求记录，未将本次规划扩大为跨供应商会话迁移或团队账单平台。

## 阻塞项（P1）

### A1：连续性保护的开关和绑定身份尚不一致

- 位置：design.md §4.3（第49–53行）、§8（第96行）；model-routing/spec.md R09。
- 问题：§4.3 要求所有路由组的 previous_response_id 都查归属，§8 又要求仅“启用本次组连续性保护”后生效，但没有该开关字段及默认值。绑定键含未定义的 credentialScope，认证变化可能改变查找键，从而作为新会话重新选路，而不是按已承诺的 continuity_unavailable 拒绝。
- 最小修复：明确一个独立的游标保护布尔项或明确与 continuity=session 的绑定关系，列出旧组/新组默认及用户可见开关。粘性查找键只包含稳定的 app/group/session 身份；凭据版本存于绑定值并比较，不能靠更换键失效。响应归属映射须包含客户端/组隔离，明确容量、TTL及首个响应 ID 的记录时点。
- 关闭验收：认证轮换、组模式开关、request 模式带游标、未知游标、跨客户端相同响应 ID、重启与淘汰均有唯一确定结果；认证变化不能隐式新建绑定并换供应商。

### A2：配置协调器锁序遗漏现有同步与 Skills 锁

- 位置：design.md §6.2（第77行），tasks.md T14。
- 证据：sync_protocol.rs 已有 sync_mutex/run_with_sync_lock（第43–55行），apply_snapshot 持 Skills 写锁（第445行）；SkillService 多个写入口内部也取同一锁。当前设计只列 operation gate→mode→DB。
- 问题：同步从旧 sync_mutex 进入新 operation gate，而普通写入从 operation gate 进入同步/Skills 内部函数时，若没有统一入口顺序与不重入约束，会产生倒序或递归持锁。T14 目前将关键顺序留给实施阶段“梳理”。
- 最小修复：明确 operation gate 与现有 sync_mutex 是合并还是有序嵌套，并写出包含 Skills 锁的完整顺序；指定外层获取锁、内部 *_under_guard 不再获取相同锁。需要网络下载的同步操作先下载/校验，再进入本地提交屏障，发布前核对修订；自动同步事件不得在屏障内同步等待自身。
- 关闭验收：至少覆盖普通 Skills 安装与环境应用、同步下载与选择恢复、自动同步回调与配置写入三组竞争；断言无死锁、迟到修订拒绝、helper 续约不依赖该屏障。

### A3：共享网关的停止范围与环境在途承诺冲突

- 位置：design.md §6.2（第79行）、project-environments/spec.md R11/R12、acceptance.md J06。
- 证据：proxy/server.rs 使用单一监听与 shutdown 通道（第56、128–148行），不是每客户端独立服务器。
- 问题：设计写“停止受影响自有网关/网络”，但 R12 要求 Claude 切方案时 Codex 不变，J06 又要求在途保持旧快照；若停共享网关或总是排空30秒，将无法同时满足这些行为。
- 最小修复：定义操作类别。仅请求策略/预算绑定变更可原子发布新的环境快照，在途不排空；修改客户端受管文件的应用使用按 app 的准入屏障并排空该 app 请求，不关闭共享 listener、不停止 Mihomo；完整恢复保留现有全局停止边界。排空超时必须解除屏障并保持旧配置。将 J06 分为上述两类。
- 关闭验收：长流 Claude A→B 的策略切换保持旧流且新流为B；文件变更遇长流则30秒busy；两个场景中 Codex 仍可持续发起并完成请求，Mihomo和系统代理不变。

### A4：尝试账本缺少派发前持久边界和升级期费用基线

- 位置：design.md §5.1–5.2、tasks.md T10/T11、budget-controls/spec.md R14、data-lifecycle/spec.md R23。
- 问题：虽规定 pending 重启转 unknown，但没有要求在任何上游字节发送前持久化 pending，也没有定义 provider/方案两份归因的结算原子性。崩溃若发生在派发与建行之间，消费将完全遗漏。升级只保留新账本则会遗漏本周期原 proxy_request_logs/rollups 已观测消费，允许已有额度被重新使用。
- 最小修复：规定 attemptId 生成与 pending 持久提交先于派发；结算以单一账本行关联 provider/环境，由同一事务更新聚合或直接查询，不能双写成两个独立真相。新预算启用时用已有日志/rollup形成去重的本周期起始额，无法证明完整性时明确 coverage unknown 并按 block_new 规则处理；定义迟到usage可从 unknown 幂等转 known，不能重复入账。
- 关闭验收：强杀在pending提交前/后、发送后/结算前；provider与方案同时限额时重复终态；有本周期旧消费的数据库升级；所有情况不得出现已派发但账本不存在且仍被当作零的请求。

### A5：缺秘密对象替换当前活动对象时没有确定处理

- 位置：design.md §6.3（第86行），data-lifecycle/spec.md R19，tasks.md T16。
- 问题：“不恢复活动指针”和“缺秘密保持待补且不激活”只覆盖新增对象。若选中的供应商或订阅以同 ID 替换当前活动对象，保留原活动指针就已引用缺凭据对象；随后恢复运行状态会尝试启用它。现有路由组/Profile/MCP 也可能引用该对象。
- 最小修复：首版采用保守明确策略：缺秘密或引用不完整的对象只有在未被当前活动选择/运行依赖使用时可作为待补对象导入；若替换活跃依赖则在预览阻止提交，用户先补凭据或显式停用/切换后再预览。不要隐式清活动指针或连带修改未选对象。预览依赖闭包须检查现有 Profile、路由组和网络活动选择。
- 关闭验收：恢复脱敏包中的同 ID 活动供应商、活动订阅、被当前方案使用的MCP分别被阻止；闲置同类对象可保存待补；未选对象和活动指针摘要始终不变。

## 非阻塞项（P2）

- **A6：新组默认 strict 的可配置入口需更明确。** 自定义模型的 tools/structuredOutput 往往unknown。建议在路由编辑器为未知能力提供现有模型元数据编辑入口及compatible解释，否则新建路由组可能在第一次调用时全部被过滤。此项可合并T08/T13，不增加模块。
- **A7：报告维度避免无谓膨胀。** 90天聚合同时包含配置修订/节点/方案可能产生很多稀疏行。建议日常图表聚合按稳定维度，具体revision留明细或单独有界关联；首版不建设完整分析平台。性能以已有V04加固定数据集验证。
