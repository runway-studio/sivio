# 实施可行性质量门 · 第一轮

- 审查日期：2026-10-28。
- 范围：brief、proposal、design、tasks、acceptance 及九份 spec；对照当前服务、schema、测试入口和原性能门槛。
- 方法：只读代码与文档，不运行业务测试、App、真实供应商或系统代理操作。
- 结论：**修订后复审**。发现 1 项 P1 阻塞、2 项 P2 改进；没有 P0。当前任务具备模块落点和大部分失败验收，但跨阶段验收口径会使任务不能按给定依赖完成。

## P1 阻塞

### F1：场景全量归属规则造成验收依赖环

证据：
- `acceptance.md`“需求—任务—场景映射”要求每项 spec 的全部 Scenario 都属于对应任务验收。
- `tasks.md:97–105` 中 T18 验收引用 J06；J06 包含 A/B 请求的快照归属、客户端出站隔离，但这些直到依赖 T18 的 T19 才实现。
- R15 的方案归因场景映射到 T11/T13/T19；T13 是 B 阶段退出点，C 阶段 T14 依赖它，方案归因却在 C 的 T19 才落地。若按“全部场景”执行，B 需要 C 的实现才能完成。

影响：任务执行者要么无法勾选前置任务，要么必须违反文档只测一部分；“每项可直接实施并验收”尚未成立。测试覆盖表按 requirement 一对多映射可以保留，但不能据此要求每个映射任务独立通过全部场景。

修订建议：
1. 明确每项任务只负责列出的子行为及验证，阶段退出收口该阶段已实现的场景；给跨阶段需求标注首次/最终验收任务。
2. T18 仅验预览版本、journal、写入/指针、回滚和恢复；J06 的请求归因/出站部分由 T19 实现，在 T20 完成全链验收。
3. T11/T13 只收口 provider 预算与无方案请求；R15 方案归因、方案预算收口在 T19/T20。保留最终 T24 全量验收。
4. 验证文档任务 DAG 无循环，并核对每个强制验收依赖没有引用后继尚未实现的行为。

关闭标准：任务与阶段矩阵明确上述归属；按顺序执行时每个前置任务都能仅凭已完成依赖满足自己的验收，不靠提前实施后继任务。

## P2 改进

### F2：预算时区与无新增依赖的取舍需要落到具体可验证模型

证据：`design.md:57` 固定“本地时区”并延迟时区修改生效；`proposal.md` 同时声明不新增第三方依赖。当前 `app/src-tauri/Cargo.toml:43` 只直接依赖 chrono，未发现已有命名时区规则库。现有 usage 查询依赖 SQLite 当前 localtime，不能直接满足独立预算时区和系统时区变化隔离。

建议：首版明确使用保存时的固定 UTC offset，并在界面说明不跟随夏令时；或明确批准小型命名时区解析依赖及其必要性。补系统时区变化、日/月边界、夏令时场景的唯一预期，避免实现者悄悄继续使用 SQLite localtime。此项不要求引入大型调度系统。

### F3：统计分位数及 Rust 验证命令仍留有可避免的占位

证据：`design.md:93` 使用固定毫秒桶，但没有桶边界或分位数取值规则；J08 要求精确匹配定义。`acceptance.md` V02 使用 `<相关filter>` 和“按当前仓库实际 feature”占位。

建议：固定一个简单的 bucket 列表及 nearest-rank/桶上界规则，或把验收改为明确可计算的误差区间；给出默认可复制的 Rust lib 与两个关键集成测试命令，再列定向过滤为可选加速。可复用：

```sh
RUSTUP_TOOLCHAIN=1.99.0 cargo test --manifest-path app/src-tauri/Cargo.toml --lib -- --test-threads=1
RUSTUP_TOOLCHAIN=1.99.0 cargo test --manifest-path app/src-tauri/Cargo.toml --test profile_roundtrip -- --test-threads=1
RUSTUP_TOOLCHAIN=1.99.0 cargo test --manifest-path app/src-tauri/Cargo.toml --test import_export_sync -- --test-threads=1
```

这些是后续实施时执行的命令，本轮未执行。最终新增测试名称应记录在实施证据中，不能以零匹配或忽略测试当通过。

## 已确认可行的部分

- 不新增独立服务或配置引擎；cmdk、hmac、sha2 和现有 Tauri/Rust/SQLite 足以支撑导航、内存绑定和索引。
- `services/profile.rs` 确实为 best-effort；提案已要求新方案走恢复协调，未误用原方法宣称原子性。
- `sync_protocol::apply_staged_configuration` 和 `restore_journal` 已有 DB/Skills 的持久恢复基础；提案明确派生文件还需扩展，不把已有能力当成完整证明。
- 当前 schema 为 22，提案不抢占固定新版本，使用下一空闲版本；保留旧版本拒绝与升级前备份。
- 五策略、十客户端/四网关/两聚合边界保留；新增 Profile 字段限制到已有可支持 scope，避免九方向变成十客户端全矩阵重写。
- UI、真实本机 HTTP/SSE、隔离恢复和原生设备测试分层合理；性能数值与原 `add-unified-ai-macos-app/acceptance.md:37–42` 一致。
- 未取得账号/硬件仅保留 NOT_VERIFIED，不伪称规划或 mock 证明生产可用。阶段构建可以有限内部交付，完整 change 仍受最终矩阵约束。

## 剩余实施风险

1. 统一写屏障将触及多个写入口，实施时须用入口清单和并发夹具证明确实覆盖，不能仅新增一把锁。
2. 第三方 usage/价格/会话 ID 不完整会降低预算与连续性可用性；unknown 和显式退出路径应保持产品可理解。
3. Intel/macOS 12、真实账号和系统授权属于外部验收资源；缺失时相应完成声明必须继续受阻。
4. 同供应商多模型需要端到端检查实际出站模型、统计键与共享认证/熔断身份；只修改 UI 校验不足。

本轮只提出一组窄范围修订。F1 关闭并核对修订未引入新阻塞后即可通过本门，不以增加更多功能或反复润色作为继续循环理由。
