# 三道质量门审查记录

审查方式：同一代理按需求、架构、实施可行性三个视角分别审查，不宣称多人独立审计。对象是规划文档，不是尚不存在的实现。上限4轮；只修阻塞、验收缺口及高价值一致性问题。

严重度：P0=方向/重大数据安全不可接受；P1=会使实现歧义或关键验收失效；P2=有边界与处置办法的实施风险；P3=表达改善。

## 第1轮：草案审查

时间：2026-10-15。已执行 OpenSpec 0.16.0 strict，结果 valid=true、issues=[]；结构通过不等于语义通过。

| 编号 | 质量门 | 级别 | 证据与问题 | 必须修订 |
| --- | --- | --- | --- | --- |
| R1 | 架构 | P1 | design D2及F18只有失败重试策略，未禁止向客户端发送流数据后跨供应商重放 | 定义重试提交点、半流失败和副作用请求边界，新增情景 |
| R2 | 架构 | P1 | design D4/D8写了Keychain和导出选项，但含密钥归档加密、旧SQL导入执行边界不明确 | 明确密钥迁移、加密导出、SQL隔离、云同步密钥处理及认证失败行为 |
| R3 | 架构/可行性 | P1 | design D6假定helper lease可恢复，没有定义helper本身被杀后的恢复者；root内核配置路径缺乏边界 | 持久快照/launchd重启恢复契约、owner核验和资源staging校验；增加双崩溃验收 |
| R4 | 需求/可行性 | P1 | F07承诺所有安装失败都保留旧版本，但第三方安装器不必具有事务语义 | 区分受管可回滚安装与外部管理源；不可保证回滚时首次提示影响，失败转修复，不以删减已支持安装能力解决 |
| R5 | 需求 | P2 | F15对OMO/专属配置仅用概括名称；F06“本文件支持表”在spec中没有实际表 | 核对实际命令名并列出边界，改引用coverage.md |
| R6 | 实施可行性 | P2 |任务有依赖文本，但尚未机器验证DAG、ID覆盖和链接；本机空间紧张 | 增加可复现文档检查记录；构建空间为M0前置，不伪造构建通过 |

本轮评分：目标18/20、业务闭环16/20、范围13/15、验收12/15、风险7/10、可执行性12/15、表达4/5，总82/100，置信度中。存在P1，不能通过质量门。下一轮只处理R1–R6并复核，不重选整体框架。

## 第2轮：针对性修订后复核

### 需求门：通过（规划）
- 用户确认范围写入proposal，不把M1/M2误称完整交付；macOS支持范围、十客户端组合、上游不支持项与排除项明确。
- 36项能力均有成功/异常情景、实施任务与阶段；F15补充OpenClaw、Hermes、OMO、Claude插件实际命令对应功能。F06支持表引用已修正。
- R4已关闭：受管源可回滚则准备恢复，不可事务回滚的已支持安装源保留安装/升级功能但明确首次影响提示及失败修复状态；未知来源不自动覆盖。
- 完整性以固定源码及T01子功能台账验收，不向未来main无限扩展；T01发现遗漏不得静默排除。此为范围核对任务，不替代本轮已给出的用户能力清单。

### 架构门：通过（规划）
- R1已关闭：design D2定义不可变请求快照、首内容块提交点、非幂等操作禁止盲目重放、重试预算；F18新增两个情景。
- R2已关闭：D4/D8明确Keychain迁移、0600边界、隔离SQL导入、默认排除秘密、认证加密云归档；F31新增两个情景。
- R3已关闭：D3定义helper持久快照、lease、launchd恢复者、睡眠重连窗口、受管资源bundle和调用方边界；F36新增两个情景。系统级后台服务彻底不可用时不承诺自动恢复，保留离线方案。
- 两类代理各自职责、端口、TUN回环、配置所有权和外部App冲突均有处理路径；一个UI体系、一个Tauri宿主，无额外插件平台或微服务。

### 实施可行性门：通过（规划；运行证据待实施）
- T01–T04是具体可执行技术验证：有输入、产物、成功条件、失败停止点，不能在未验证时跳过并大规模迁移页面。
- T05–T28各有职责、依赖、产物、验收和初始人日范围；M0后的任务“可按依赖执行”不等于当前全部ready。
- R6已关闭：OpenSpec strict和需求/任务/链接/DAG检查实际执行通过；没有应用代码或产品任务被标为完成。
- 本机约6.1GiB可用空间不足以保证大规模Rust构建；已列T02前置空间检查。签名、两架构真机、测试账号、订阅和云存储凭据未冒充现成资源。
- helper/内核代码并非可直接嵌入SDK；当前结论是方案具有可执行验证路线，不是已证明所有移植能一次构建成功。
